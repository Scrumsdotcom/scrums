# Scenario: Monthly close (finance-ops)

This scenario walks through the **end-to-end execution of a monthly close** as orchestrated by Company-as-Code. The goal is to make the primitives' composition visible: how an initiative's success criteria translate into a workflow, how the workflow enforces the 5-step sync verification protocol, and how the audit log + typed event ledger record everything along the way.

> Time horizon: a single calendar month boundary, roughly the first business day after period end.

## Day 0 — Pre-close (the previous month)

The `cash-forecaster` agent has been running daily under `autonomous` cadence (`schedule: "0 7 * * *"`) producing a rolling 13-week forecast. Each invocation:

1. Reads canonical ledger entries (via the `ledger-summary` interface this module exposes to itself for self-consumption)
2. Reads forward pipeline state from [`sales`](../../company/domains/sales-marketing/sales) via the `pipeline-state` interface
3. Reads workforce commitments from [`people`](../../company/domains/finance-ops/people) via the `workforce-state` interface
4. Produces a `cash-forecast` output
5. Emits `finance.cash_forecast_updated` *only when the forecast value differs from the previous by ≥1%* (the invariant on the agent)
6. Writes an audit record under topic `cash-forecaster` regardless

The CFO reads the brief generated by the `cash-forecast-summary` prompt every Monday — ≤ 5 bullets per the [feedback memory](../../company/memory/cash-forecaster/cfo-format-preference.md).

This is the **autonomous baseline**. No human is in the loop because there is no external write.

## Day 1 — Close-eligible day

The first business day after period end. The finance-lead opens the admin surface and queues the `month-end-close` workflow for the period. The workflow is `hitl: true`; it cannot fire on a schedule.

### Step 1 — Baseline

The workflow's first step (`id: baseline`, `kind: agent`) invokes `cash-forecaster`. The agent runs in **read-only** mode, captures current state, and writes a baseline audit record. The runtime assigns this invocation a correlation ID — every subsequent step in this scenario will reference it.

**Audit row 1** lands under topic `cash-forecaster` with:

- `correlationId: close-2026-04-<ulid>`
- `actor: people:finance-lead`
- `action: cash-forecaster.baseline`
- `output`: cash position, A/R, deferred revenue, recognized revenue
- `status: success`

### Step 2 — Dry-run

The workflow's second step (`id: dry-run-close`, `kind: dry-run`, `dryRunRequired: true`) invokes the `post-period-close` automation with `dryRun: true`. The automation:

1. Reads canonical ledger entries for the period
2. Computes the period-close journal entry it *would* post
3. Writes an audit record marked `dryRun: true` with the projected payload
4. **Mutates nothing external**

**Audit row 2** under topic `post-period-close`:

- Same correlation ID
- `action: post-period-close`
- `dryRun: true`
- `output`: the exact projected journal entry
- `status: dry-run`

### Step 3 — Confirm counts (human approval)

The workflow advances to `id: confirm` (`kind: human-approval`). The finance-lead reads the projected journal entry from audit row 2, compares it against the baseline from row 1, and confirms the delta is sensible.

The policy applied here is [`hitl-external-writes.md`](../../company/policies/hitl-external-writes.md): the ledger is an external surface (the journal posts through an accounting integration), so the write is human-gated by default.

**Audit row 3** under topic `month-end-close-approval`:

- Same correlation ID
- `action: human-approval`
- `actor: people:finance-lead` (canonical Person ID)
- `decision: approved`

If the finance-lead observes that the projection is wildly off (a > 10% delta from baseline on any account), the playbook says **stop and escalate to the CFO**. The approval is withheld; the workflow halts; a TASK opens with the playbook ID in the title.

### Step 4 — Live close

With approval captured, the workflow advances to `id: live-close` (`kind: live-write`). The same `post-period-close` automation runs with `dryRun: false`. The automation:

1. Re-validates the audit record from row 3 confirms approval exists for this correlation ID. The runtime refuses to advance past this check otherwise (the invariant on the automation enforces it).
2. Posts the journal entry to the canonical ledger.
3. Emits `finance.period_closed` with the period and the resulting ledger state hash.
4. Writes an audit record.

`onFailure: escalate, retries: 0` — there is no retry path. A failure here pages the CFO and opens an incident.

**Audit row 4** under topic `post-period-close`:

- Same correlation ID
- `dryRun: false`
- `causationId` = row 2's ID (the dry-run that preceded it)
- `status: success`

**Event row 1** in the typed event ledger:

- `type: finance.period_closed`
- `entity.canonicalId: PERIOD-2026-04`
- `actor: people:finance-lead`
- `occurredAt: <timestamp>`

### Step 5 — Re-verify

The workflow's final step (`id: re-verify`, `kind: agent`) re-invokes `cash-forecaster`. The agent re-queries the canonical ledger and confirms state shifted exactly as the dry-run predicted. Drift > 0.5% on cash position is an incident.

**Audit row 5** under topic `cash-forecaster`:

- Same correlation ID
- `action: cash-forecaster.re-verify`
- `output`: post-close cash position, A/R, deferred revenue, recognized revenue
- `status: success` (or incident if drift detected)

## Day 1.5 — The audit narrative

Querying the audit log by correlation ID returns the full narrative in order:

```
close-2026-04-<ulid>:
  1. cash-forecaster.baseline      (autonomous baseline)
  2. post-period-close             (dryRun: true)
  3. human-approval                (finance-lead approved)
  4. post-period-close             (dryRun: false, success)
  5. cash-forecaster.re-verify     (state matches projection)
```

The typed event ledger contains one row: `finance.period_closed`. The audit log contains the **how**; the event ledger contains the **what changed**.

## Day 2 — Metric impact

The next daily run of `cash-forecaster` reads the now-closed period. The `METRIC-FIN-CLOSE-ON-TIME` metric, which has lineage on `period_closed_at`, updates: this close completed within 2 business days, so it counts as on-time.

The metric appears on the [`finance-overview`](../../company/dashboards/finance-overview.yaml) dashboard. The threshold (`warning: lt 95%`, `critical: lt 80%`) hasn't been breached.

`GOAL-FIN-0001` (the on-time SLA) reads `status: on-track` because the rolling 90-day average is above the target.

`INIT-FIN-0001` (the initiative driving this automation) shows progress against its milestone "Three consecutive closes under SLA" — close #2 of 3.

## What this scenario demonstrates

- **Plan-first, declare-first.** The initiative existed before the workflow. The goal pointed at a metric that existed before the goal. Every primitive carried its weight.
- **One writer per field.** The ledger has one writer (`post-period-close`). The cash position is *read* by the agent, never written.
- **Dry-run is mandatory.** Step 2 is not optional. The automation refuses step 4 without it.
- **HITL is declarative.** The workflow's `hitl: true` and the automation's "requires prior approval" invariant are both declarative; the runtime enforces both.
- **Audit log + typed event ledger are separate.** Five audit rows answered "what did we do"; one event row answered "what happened to the entity."
- **The cognition tree composes naturally.** The finance-ops executive's `finance-rollup` will surface this close on next Monday's executive brief without any extra wiring.

## What would change for a different scenario

- If the same protocol were applied to a **new payroll integration**, only the automation, workflow, integration manifest, and per-agent context bundles would change. The 5-step shape stays.
- If the close were ever promoted to `autonomous`, the procedure is: accumulate ≥3 evidence runs, open an ADR citing the correlation IDs, update the manifest's HITL declaration in the same PR. See [`/company/policies/hitl-external-writes.md`](../../company/policies/hitl-external-writes.md).
