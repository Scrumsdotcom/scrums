# Requirements

Obligations the company is held to. A certification clause, a regulation
article, a contractual commitment, or a rule the company imposes on itself.

A Requirement states **what** must be true. It does not state how, and it does
not list the Controls that make it true. Coverage is declared one way, by the
Control, so the two lists can never disagree with each other.

## The rules

- An `in-scope` requirement with no operating Control fails validation. That is
  the whole point of the layer: a gap becomes a build failure instead of an
  audit finding.
- An `out-of-scope` requirement carries a written `scopeRationale`. A silent
  exclusion is the thing auditors look for.
- `statement` is written in the company's own words. Do not paste copyrighted
  standard text into the repository.
- Canonical IDs are permanent. A requirement that is retired keeps its ID and
  changes status.

## Where the coverage view lives

[`/generated/control-matrix.json`](../../generated/control-matrix.json), which
inverts the Controls' `implements` lists into per-requirement coverage, per
framework totals, and an explicit `gaps` array. It is regenerated by
`cac generate` and drift-gated like every other generated artefact.
