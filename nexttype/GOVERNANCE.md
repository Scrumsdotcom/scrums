# Proposed NextType governance

This template describes the future standalone project.
The repository owner must name maintainers and ratify this process before publication.

| Role | Decision responsibility |
| --- | --- |
| Requirement owner | Intent, contracts, supported input domains, permissions, and changed guarantees. |
| Language maintainer | Core semantics, IR, protocol, compatibility, and accepted language proposals. |
| Assurance maintainer | Proof profiles, trusted assumptions, independent checking, and verification claims. |
| Implementation maintainer | Compiler, runtime, library, and target changes within existing contracts. |
| Release maintainer | Reproducible artifacts, publication authority, provenance, and rollback. |
| Conduct moderator | Confidential reports, fair review, conflicts of interest, and proportionate action. |

The implementation agent cannot serve as its own approval authority.
A proof does not ratify a requirement.
A maintainer approval does not replace proof and test obligations.

Language proposals include alternatives, semantics, conformance cases, compatibility, and token-cost impact.
Accepted proposals receive versioned decision records.
Breaking changes require migration and supported-version plans.

Publish uncertainty and negative benchmark results.
Keep targets separate from measured claims.
Record unresolved decisions in the project plan rather than inventing defaults for legal or publishing authority.
